Pagination, measured: OFFSET vs keyset

LIMIT 20 OFFSET 40 is the first way most of us learn to page through results. It gets slower with every page, and when rows are added or deleted between page loads, it shows some twice and skips others. Here is how much, and what to use instead.

Published 2026-10-13 · SQLite 3.49.1 · 1,000,000 rows · one laptop · lab code

Last page, OFFSET
26.8 ms
LIMIT 20 OFFSET 999980
Last page, keyset
0.022 ms
WHERE (created_at, id) < (?, ?)

Medians of repeated runs on an in-memory database, so no disk and no network are involved. Same table, same index, same 20 rows returned. Page 1 took 0.021 ms both ways.

Both queries use the same index, and both plans look fine at a glance. The difference is that OFFSET has to walk past every row before the page it returns, so its cost grows with the page number. Keyset pagination starts from where the last page ended, so every page costs the same. Below: the measurements, the correctness problem that matters even on small tables, and what keyset can't do.

The setup

A table of 1,000,000 synthetic posts, shown newest first, 20 per page, with an index that matches the sort order:

CREATE TABLE posts (id INTEGER PRIMARY KEY, created_at INTEGER, author TEXT, title TEXT);
CREATE INDEX idx_created ON posts(created_at, id);

-- OFFSET: page n
SELECT id, created_at, author, title FROM posts
 ORDER BY created_at DESC, id DESC
 LIMIT 20 OFFSET :skip;                 -- skip = (n - 1) * 20

-- keyset: the page after the row (:c, :i), the last row of the previous page
SELECT id, created_at, author, title FROM posts
 WHERE (created_at, id) < (:c, :i)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;

Three posts share each created_at value on purpose, because real timestamps collide too. That's why id is in the sort order and in the index: with it, every row has a unique position.[2] For every page measured, the lab checked that both queries returned the same 20 rows.

OFFSET reads the rows it skips

OFFSET doesn't jump anywhere. SQLite's documentation spells it out: it "computes the query as "LIMIT x+y" and discards the first y values without returning them to the application", so OFFSET "requires time proportional to the offset value".[1] PostgreSQL's documentation says the same: "The rows skipped by an OFFSET clause still have to be computed inside the server; therefore a large OFFSET might be inefficient."[2]

PageRows skippedOFFSETkeysetOFFSET VM instructions

Median time per query. VM instructions are the steps SQLite's bytecode engine ran, counted every 100 instructions. Keyset ran 300 on every page after the first.

The work grows in a straight line. Page 1,000 skips 19,980 rows and took 0.54 ms. Page 10,000 skips ten times as many and took 5.4 ms, also ten times as much. The VM instruction count tells the same story: about three instructions per skipped row, from 200 on page 1 to 3,000,100 on the last page. Keyset took 0.021–0.023 ms on every page, a figure that includes Python's own call and fetch overhead.

The plans don't warn you. OFFSET's is SCANposts USING INDEX idx_created: it does use the index, to read rows already sorted, but it reads them from the first one. Keyset's is SEARCHposts USING INDEX idx_created (created_at<?): it starts in the middle of the index.[4] If you read the indexes article, that's the same SCAN versus SEARCH difference, only hidden behind a LIMIT.

Selecting less doesn't fix it. Asking only for id lets SQLite answer from the index alone (SCAN posts USING COVERING INDEX idx_created), and the last page still took 11.1 ms: cheaper per row, still every row.

OFFSET also shows wrong rows when data changes

Speed only matters on deep pages. This problem shows up on page 2. An OFFSET says "skip the first 20 rows as they are now", and the rows may have moved since page 1 was read. The lab read page 1, changed the table, then read pages 2 and 3:

Between page 1 and page 2…OFFSETkeyset
5 newer posts arrivethe last 5 rows of page 1 shown again on page 2no repeats
5 posts on page 1 are deleted5 rows never shown: they moved onto page 1, which was already readnothing missed

A feed where new posts arrive while you scroll gets duplicates. A list where you delete or archive items as you go silently skips some. Keyset is immune because its cursor is a row, not a position: "everything after this post" means the same thing however many posts arrived in front of it.

The tie-breaker is not optional

The keyset condition has to point at exactly one row, so the sort must be unique. A row value comparison like (created_at, id) < (:c, :i) compares left to right and stops at the first pair that differs[3], which is exactly "earlier timestamp, or same timestamp and smaller id".

Drop the id and write WHERE created_at < :c, and every page that ends in the middle of a group of equal timestamps silently skips the rest of that group. The lab walked through all 50,000 pages both ways. With (created_at, id) it returned 1,000,000 rows, each once. With created_at alone it returned 952,380: 47,620 posts never appeared, and nothing errored.

Row values arrived in SQLite 3.15.0 (2016).[1] In PostgreSQL the same (a, b) < (x, y) syntax works.[3] One caveat: if one of the sort columns can be NULL, the comparison can come out unknown instead of true or false[3], so keep keyset columns NOT NULL or handle NULLs explicitly.

      What keyset can't do

      • Jump to page 437. A keyset cursor only knows "the page after this row" (and, with the comparison and order flipped, "the page before"). Numbered page links need an offset somewhere. For infinite scroll, "load more" and API cursors, that's no loss.
      • Sort by anything you like. Each sort order needs its own unique key, its own condition, and an index that matches, or the keyset query isn't fast either.[1]
      • Show "page X of Y" by itself. A total still needs a count(*). On this SQLite table that was cheap, 0.18 ms. We didn't measure other databases, so don't assume it is everywhere.

      If you need numbered pages, OFFSET is fine for the first few. On page 10 it took 0.026 ms against keyset's 0.023 ms. The cost only shows up deep in the list, so capping how far users (and crawlers) can page is a reasonable compromise.

      Rules of thumb

      1. For feeds, infinite scroll and API pagination, use keyset: WHERE (sort_col, id) < (:last_sort, :last_id) ORDER BY sort_col DESC, id DESC LIMIT n, and return the last row's values as the cursor.
      2. Always end the sort with a unique column, usually the primary key, in both ORDER BY and the cursor.
      3. Index exactly that order, e.g. (created_at, id). Without a matching index, keyset is just a slower filter.
      4. If you keep OFFSET, cap the page number, and expect duplicates and gaps while data changes.
      5. Check the plan: OFFSET pagination shows up as a SCAN, even with an index, while keyset shows SEARCH.
