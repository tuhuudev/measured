# Fact sheet: retries, measured

Every claim in the article maps to these IDs. Levels: established / simplified / contested. Measured rows come from `retry_lab.py` → `results.json` (canonical run 2026-10-12; machine and versions in the JSON). Ranges quote the medians of three full lab runs that day.

| ID | Claim | Level | Source |
|---|---|---|---|
| F1 | HTTP 503 (Service Unavailable) means the server is temporarily unable to handle the request because of overload or maintenance, likely alleviated after some delay; the server MAY send `Retry-After`. | established | [RFC 9110 §15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#name-503-service-unavailable) ("indicates that the server is currently unable to handle the request due to a temporary overload or scheduled maintenance, which will likely be alleviated after some delay"; "The server MAY send a Retry-After header field"). Checked 2026-10-12. |
| F2 | Capped exponential backoff: after each failed attempt the client multiplies its wait by a constant, up to a maximum. | established | [AWS Architecture Blog: Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) ("Capped exponential backoff means that clients multiply their backoff by a constant after each attempt, up to some maximum value."); [AWS Builders' Library: Timeouts, retries, and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter) ("This is called, predictably, capped exponential backoff."). Checked 2026-10-12. |
| F3 | When failures come from overload or contention, backoff alone helps less than expected: if all failed calls back off to the same time, they collide again when retried. Jitter adds randomness to the backoff to spread retries in time. | established | [AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter) ("When failures are caused by overload or contention, backing off often doesn't help as much as it seems like it should. This is because of correlation. If all the failed calls back off to the same time, they cause contention or overload again when they are retried. Our solution is jitter."; "Jitter adds some amount of randomness to the backoff to spread the retries around in time."). Checked 2026-10-12. |
| F4 | AWS's simulation found that backoff alone "helps a small amount, but doesn't solve the problem"; "the no-jitter exponential backoff approach is the clear loser"; it names the variant that waits a random time between zero and the capped backoff "Full Jitter". | established | [AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) (quotes as given; the Full Jitter formula is shown as an image in the article, matching the lab's `random(0, min(CAP, BASE * 2**n))`). Checked 2026-10-12. |
| F5 | Google's SRE book: always use randomized exponential backoff when scheduling retries; limit retries per request; consider a server-wide retry budget (for example 60 retries per minute per process, failing the request once it's exceeded). | established | [Google SRE book: Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/) ("Always use randomized exponential backoff when scheduling retries."; "Limit retries per request."; "Consider having a server-wide retry budget. For example, only allow 60 retries per minute in a process, and if the retry budget is exceeded, don't retry; just fail the request."). Checked 2026-10-12. |
| F12 | A method is idempotent if repeating identical requests has the same intended effect as one; idempotent requests can be repeated automatically after a communication failure; a client SHOULD NOT automatically retry a non-idempotent request unless it knows the semantics are idempotent or can detect the original was never applied. | established | [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods) (quotes as given). Checked 2026-10-12. |
| F6 | Lab setup: a real asyncio TCP server in its own process on localhost serves at most 20 requests at once, 20 ms each, and answers "busy" at once when full. 200 clients send one request at the same moment and retry on "busy", at most 10 attempts each; backoff base 10 ms, cap 1,000 ms. With perfect scheduling the 200 requests need 200 / 20 × 20 ms = 200 ms. | established | Lab `labs/retries/retry_lab.py`. Checked 2026-10-12. |
| F7 | Measured, retry immediately: a median 1,512 requests reached the server for 200 clients; 120 of 200 clients gave up after 10 attempts (range across runs: 100–120); the 80 that succeeded were served at a median 41 ms, the last at 74.5 ms. | established | Lab → `policies.immediate` (canonical run); ranges from three runs. Checked 2026-10-12. |
| F8 | Measured, capped exponential backoff without jitter: all 200 clients succeeded (in some trials up to 5 gave up), with a median 1,063 requests; the last client finished at 3,307 ms (range of run medians: 2,379–3,330 ms); the median client at 189 ms. Retries arrive in synchronized waves (visible in the timeline). | established | Lab → `policies.backoff`, `timeline`. Checked 2026-10-12. |
| F9 | Measured, full jitter: all 200 clients succeeded with a median 901 requests; the last client finished at 459 ms (range of run medians: 459–535 ms; the single trial drawn in the timeline finished at 686 ms); the median client at 95 ms. | established | Lab → `policies.jitter`. Checked 2026-10-12. |
| F10 | Limitation: all 200 clients share one Python event loop, which batches sends within a few milliseconds. The noise affects every policy: it bunches jittered retries a little and breaks up some of backoff's waves (the noise-free simulation, M1, is harsher on backoff than the lab, while jitter lands close to the lab). Its net effect on the gap is not measured. Timelines are shown in 50 ms buckets. | established | Lab observation 2026-10-12 (raw arrival times clustered at a few ms intervals). |
| F11 | Lab correction: on Windows, `asyncio.sleep` is rounded up to the ~15.6 ms system timer tick by default (a 20 ms sleep measured ~32.6 ms; a 1 ms sleep ~13.9 ms); the lab requests a 1 ms timer with `timeBeginPeriod(1)` (then 20 ms measured ~20.6 ms). | established | Lab probe 2026-10-12. |

## Simulation used by the interactive part
| ID | What | Level | Note |
|---|---|---|---|
| M1 | A discrete-event simulation in the page (`retries/sim.js`): same server model (capacity 20, 20 ms per request, instant "busy"), same policies, a chosen number of clients and a chosen round-trip time; seeded random numbers. At 200 clients and the default round trip (about 0.6 ms), over seeds 1–30: jitter sent a median 971 requests and its last client finished at a median 451 ms (range 378–964 ms); plain backoff left 20 clients without attempts; immediate retries left 180 failing. | simplified | No OS scheduling noise, so waves without jitter stay perfectly aligned; labelled "simulation", shown next to the measured run. Reproduce with Node: `require('./retries/sim.js').simulate({...})`. |

## Simplifications register
| # | Simplification | Why it is OK | On-page caveat |
|---|---|---|---|
| S1 | The server rejects instantly when full; real servers may queue, slow down or time out. | Isolates the retry timing question; RFC 9110's 503 is the matching real-world signal. | "answers busy at once, like a 503" |
| S2 | One burst of clients at t = 0, no new traffic. | The thundering herd case the sources describe; ongoing traffic makes retries worse, not better. | Stated in setup. |
| S3 | Only three policies; equal/decorrelated jitter, retry budgets and `Retry-After` are described, not measured. | Keeps the comparison readable. | "not measured here" |
