# Fact sheet: database indexes, measured

Every claim in the article maps to these IDs. Levels: established / simplified / contested. Measured rows come from `index_lab.py` → `results.json` (run 2026-10-08). Originally prepared for a video version of this topic.

| ID | Claim | Level | Source |
|---|---|---|---|
| F1 | Without an index, the database must scan the entire table, row by row, to find matching rows. | established | [PostgreSQL: Indexes intro](https://www.postgresql.org/docs/current/indexes-intro.html) ("the system would have to scan the entire test1 table, row by row, to find all matching entries"); [SQLite: Query planning](https://www.sqlite.org/queryplanner.html) ("This algorithm is called a full table scan"). Checked 2026-10-06. |
| F2 | With an index, the database can walk a few levels down a search tree instead of scanning. | established | [PostgreSQL: Indexes intro](https://www.postgresql.org/docs/current/indexes-intro.html) ("it might only have to walk a few levels deep into a search tree"). Checked 2026-10-06. |
| F3 | A B-tree index is a multi-level tree of pages: internal pages point to the next level down, leaf pages hold entries that point to table rows. | established | [PostgreSQL: B-Tree implementation](https://www.postgresql.org/docs/current/btree.html) (leaf pages "contain tuples that point to table rows"; internal pages "point to the next level down in the tree"). Checked 2026-10-06. |
| F4 | An index keeps the indexed column's values in sorted order, each with a pointer to its row, so a lookup costs about log N instead of N. | established | [SQLite: Query planning](https://www.sqlite.org/queryplanner.html) (index rows stored "in content order" with the rowid; lookup "proportional to logN rather than being proportional to N"). Checked 2026-10-06. |
| F5 | A B-tree index serves equality and range conditions on sortable data: `<`, `<=`, `=`, `>=`, `>`, plus `BETWEEN` and `IN`. | established | [PostgreSQL: Index types](https://www.postgresql.org/docs/current/indexes-types.html) ("B-trees can handle equality and range queries on data that can be sorted into some ordering"). Checked 2026-10-06. |
| F6 | A pattern not anchored at the start, such as `LIKE '%bar'`, cannot use a B-tree index to narrow the search. | established | [PostgreSQL: Index types](https://www.postgresql.org/docs/current/indexes-types.html) (B-tree for LIKE only "if the pattern is a constant and is anchored to the beginning of the string … but not col LIKE '%bar'"). Checked 2026-10-06. |
| F7 | Measured on an in-memory SQLite database: 1,000,000 rows, one email lookup took a median 64.2 ms with no index (`SCAN users`) and 0.0031 ms with an index on email (`SEARCH … USING COVERING INDEX idx_email (email=?)`); a `BETWEEN 'user5' AND 'user6'` range on email was also a `SEARCH` (the video draws bounds 'user4'..'user8' for readability; the plan shape does not depend on the literals). | established | Our lab `labs/indexes/index_lab.py`, `results.json` (SQLite 3.49.1, Python 3.12.10, AMD64 laptop); plan terms per [SQLite: EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) ("SCAN is used for a full-table scan … SEARCH indicates that only a subset of the table rows are visited"). Checked 2026-10-08. |
| F8 | Measured: with the email index present, a lookup on an unindexed column (`name`, 69.3 ms) and a `LIKE '%…'` pattern on email were both `SCAN`s (the second scans the whole index). | established | Same lab and results; [SQLite: EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) ("SCAN … including cases where SQLite iterates through all records in a table in an order defined by an index"). Checked 2026-10-08. |
| F9 | After an index is created, the system must keep it synchronized with the table, which adds overhead to inserts, updates and deletes. | established | [PostgreSQL: Indexes intro](https://www.postgresql.org/docs/current/indexes-intro.html) ("This adds overhead to data manipulation operations."). Checked 2026-10-06. |
| F10 | When a leaf page is full on insert, it splits: part of its entries move to a new page and the parent gets a new pointer; splits can cascade, and a root split adds a level. | established | [PostgreSQL: B-Tree implementation](https://www.postgresql.org/docs/current/btree.html) (page split moves "a portion of items to a new page"; a "downlink" is added to the parent; root split adds a level). Checked 2026-10-06. |
| F11 | B-tree is the default index type in PostgreSQL. | established | [PostgreSQL: Index types](https://www.postgresql.org/docs/current/indexes-types.html) ("By default, the CREATE INDEX command creates B-tree indexes"). Checked 2026-10-06. |
| F12 | An index can deliver rows already in sorted order, so `ORDER BY` needs no separate sort; with `ORDER BY … LIMIT n` the first n rows come straight from the index without scanning the rest. | established | [PostgreSQL: Indexes and ORDER BY](https://www.postgresql.org/docs/current/indexes-ordering.html) ("This allows a query's ORDER BY specification to be honored without a separate sorting step"; "if there is an index matching the ORDER BY, the first n rows can be retrieved directly, without scanning the remainder at all"). Checked 2026-10-08. |
| F13 | Measured: `ORDER BY email LIMIT 10` took 93.7 ms without an index (`SCAN users` + `USE TEMP B-TREE FOR ORDER BY`, i.e. a sort) and 0.0052 ms with the email index (no temp b-tree). | established | Lab and results; [SQLite: EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) ("USE TEMP B-TREE FOR xxx" marks a temporary b-tree used to sort for ORDER BY). Checked 2026-10-08. |
| F14 | A plain index on a column is not used for a condition on a function of that column, such as `lower(email) = …`; an index on the expression itself is, if the query writes the same expression. Expression indexes cost extra on every insert and update. | established | [PostgreSQL: Indexes on expressions](https://www.postgresql.org/docs/current/indexes-expressional.html) (`CREATE INDEX test1_lower_col1_idx ON test1 (lower(col1))`; "relatively expensive to maintain, because the derived expression(s) must be computed for each row insertion"); [SQLite: Indexes on expressions](https://www.sqlite.org/expridx.html) (used when the expression appears "exactly as it is written in the CREATE INDEX statement. The query planner does not do algebra"). Checked 2026-10-08. |
| F15 | Measured: `WHERE lower(email) = ?` with only the plain email index was a `SCAN` taking 196.9 ms; with an index on `lower(email)` it was a `SEARCH` taking 0.0031 ms. | established | Lab and results; plan terms per [SQLite: Indexes on expressions](https://www.sqlite.org/expridx.html). Checked 2026-10-08. |
| F16 | A multi-column index is sorted by its leftmost column first, the next column breaking ties; it is most efficient when the query constrains the leading columns, while conditions only on later columns do not necessarily narrow the part of the index that must be read. | established | [SQLite: Query planning](https://www.sqlite.org/queryplanner.html) ("The left-most column is the primary key used for ordering the rows in the index. The second column is used to break ties in the left-most column."); [PostgreSQL: Multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html) ("most efficient when there are constraints on the leading (leftmost) columns"; constraints on columns to the right "do not necessarily reduce the portion of the index that has to be scanned"). Checked 2026-10-08. |
| F17 | Some databases can still use a multi-column index without a condition on its first column ("skip scan"), when that first column has few distinct values: SQLite only after `ANALYZE` has measured the duplicates; PostgreSQL 18's B-tree can too. | established | [SQLite: Query optimizer overview §6](https://www.sqlite.org/optoverview.html) ("a skip-scan is never used on a database that has not been analyzed"); [PostgreSQL 18: Multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html) ("given an index on (x, y), and a query condition WHERE y = 7700, a B-tree index scan might be able to apply the skip scan optimization … only taken when there are so few distinct x values"). Checked 2026-10-08. |
| F18 | Measured, index on `(last_name, first_name)` with 1,000 distinct last names: both columns 0.0038 ms (`SEARCH`); `first_name` alone 63.9 ms (`SCAN`, no statistics); `first_name` alone after `ANALYZE` 2.55 ms (`SEARCH … ANY(last_name) AND first_name=?`, a skip scan). | established | Lab and results; [SQLite: Query optimizer overview §6](https://www.sqlite.org/optoverview.html). Checked 2026-10-08. |
| F19 | Measured: the email index on 1,000,000 rows, read from the database file, has 4,096-byte pages in 3 levels, with 7,519 leaf pages holding about 132 entries each. In SQLite's index B-trees, interior pages hold keys too (7,518 of the 1,000,000 entries). | established | Lab (`index_shape` in results); page layout per [SQLite: Database file format §1.6](https://www.sqlite.org/fileformat2.html) (interior index b-tree page flag 0x02, leaf 0x0a; interior index cells carry a key payload). Checked 2026-10-08. |
| F20 | Measured: adding the email index grew the database from 59,129,856 to 90,193,920 bytes (+31.1 MB, +53%). | established | Lab (`size` = `PRAGMA page_count` × 4,096-byte pages, per [SQLite: PRAGMA page_count](https://www.sqlite.org/pragma.html#pragma_page_count)). Checked 2026-10-08. |
| F21 | Measured: inserting 200,000 rows took 374 ms with no secondary index, 551 ms with one, and 1,015 ms with three. | established | Lab (`insert_200k_ms` in results); consistent with [PostgreSQL: Indexes intro](https://www.postgresql.org/docs/current/indexes-intro.html) ("adds overhead to data manipulation operations"). Checked 2026-10-08. |
| F22 | `EXPLAIN` shows the plan the database chose: in PostgreSQL a full scan appears as `Seq Scan` and an index lookup as `Index Scan`; in SQLite, `EXPLAIN QUERY PLAN` prints `SCAN` or `SEARCH`. PostgreSQL also shows `Index Only Scan` and `Bitmap Index Scan` / `Bitmap Heap Scan`. | established | [PostgreSQL: Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html) ("You can use the EXPLAIN command to see what query plan the planner creates for any query"; `Seq Scan on tenk1`, `Index Scan using tenk1_unique1 on tenk1`); [SQLite: EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html). Checked 2026-10-08. |
| F23 | `COVERING INDEX` in a SQLite plan means the index alone holds every column the query needs, so the table itself is not read. | established | [SQLite: EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html) (example `SEARCH t1 USING COVERING INDEX i2 (a=?)`; covering index section). Checked 2026-10-08. |
| F24 | To return several matches, the index is searched once for the first matching entry, then the following entries are read in order; each level of a B-tree is also linked to its neighbours. | simplified | [SQLite: Query planning §1.4](https://www.sqlite.org/queryplanner.html) ("a single binary search to find the first entry … instead of quitting, the database engine then advances to the next row of index"); [PostgreSQL: B-Tree implementation](https://www.postgresql.org/docs/current/btree.html) ("each level of the tree can be used as a doubly-linked list of pages"); our range plan `SEARCH … (email>? AND email<?)` (F7). Checked 2026-10-08. |
| F28 | In SQLite, a column declared `INTEGER PRIMARY KEY` is an alias for the rowid, and every index entry stores the rowid. | established | [SQLite: CREATE TABLE, ROWIDs and the INTEGER PRIMARY KEY](https://www.sqlite.org/lang_createtable.html#rowid) ("the column becomes an alias for the rowid"); [SQLite: Query planning §1.3](https://www.sqlite.org/queryplanner.html) (index content "stored in front of the rowid"). Checked 2026-10-12. |
| F29 | In PostgreSQL, an update avoids new index entries (a heap-only tuple, HOT) only when it modifies no column referenced by the table's indexes (summarizing indexes aside) and the old row's page has free space for the new version. | established | [PostgreSQL: Heap-Only Tuples](https://www.postgresql.org/docs/current/storage-hot.html) ("The update does not modify any columns referenced by the table's indexes, not including summarizing indexes."; "There is sufficient free space on the page containing the old row for the updated row."; "New index entries are not needed to represent updated rows"). Checked 2026-10-12. |

## Simplifications register
| # | Simplification | Why it is OK | On-screen caveat |
|---|---|---|---|
| S1 | Most index pages are drawn with 3 keys; real leaf pages hold about 132 (F19), which the video states once with the measured numbers. | Readable; the real numbers are shown where they matter. | "real: 4 KB pages · ~132 entries per leaf" |
| S2 | Only B-tree indexes; hash, GIN, BRIN, partial and unique indexes are left out. | One family, the default (F11). | None |
| S3 | We make no claim about prefix patterns (`LIKE 'abc%'`): in PostgreSQL it depends on locale/operator class, in SQLite on case sensitivity. | Avoids a conditionally true claim. | None |
| S4 | Timings come from an in-memory SQLite database on one laptop (no disk I/O, no client round-trip); PostgreSQL and other machines give other numbers. The gaps are the point. | Real measurements, labelled. | "measured: SQLite in memory · 1M rows · one laptop" |
| S5 | The table is drawn as a stack of row cards; real rows live in pages. | The scan-every-row idea is what matters. | None |
| S6 | "Every insert updates every index": partial indexes skip non-matching rows, and some updates avoid index changes (PostgreSQL HOT). | True for plain column indexes and inserts, the case measured. | None |
| S7 | The tree drawing follows PostgreSQL's description (separator keys in upper pages, entries in leaves); SQLite also keeps a small share of entries in interior pages (F19). | Narration only claims what both share: sorted, a few levels, walked top-down. | None |
| S8 | Lab queries select only indexed columns, so SQLite reports covering indexes (F23); a `SELECT *` would also visit the table after the index lookup. | Plans are shown verbatim; the covering note is explained once. | "covering: the index alone answers" |
| S9 | Skip scan is measured only in SQLite; PostgreSQL 18's conditions are stated from its docs, not measured. | Stated as "some databases, when the first column has few values". | "after ANALYZE · SQLite" |
| S10 | Insert timings are an in-memory batch insert; disk, WAL and concurrency add more cost on a real server. | The ratio between 0, 1 and 3 indexes is the point. | "measured: in-memory batch insert" |
| S11 | Range scans are described as "one walk, then a slide along the leaves": SQLite's docs describe this for repeated equal values, PostgreSQL's for linked pages; neither page spells out a range scan step by step (F24). The dotted links between leaves are drawn as in PostgreSQL; SQLite's pages have no sibling pointers (its cursor climbs back through the parent). | It is the standard B-tree access path and matches the measured `SEARCH` plan. | None |
