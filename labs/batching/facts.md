# Fact sheet: batching writes, measured

Every claim in the article maps to these IDs. Levels: established / simplified / contested. Measured rows come from `batching_lab.py` → `results.json` (run 2026-10-13).

| ID | Claim | Level | Source |
|---|---|---|---|
| F1 | By default each INSERT is its own transaction; wrapping many INSERTs in `BEGIN` … `COMMIT` makes them one transaction, and the commit cost is amortized over all of them. | established | [SQLite FAQ #19](https://www.sqlite.org/faq.html#q19) ("By default, each INSERT statement is its own transaction. But if you surround multiple INSERT statements with BEGIN...COMMIT then all the inserts are grouped into a single transaction. The time needed to commit the transaction is amortized over all the enclosed insert statements"). Checked 2026-10-13. |
| F2 | SQLite can do far more inserts than transactions per second, because by default a commit waits until the data is safely on the disk. The FAQ's numbers date from spinning disks, but its 2024 update says the gist still holds. | established | [SQLite FAQ #19](https://www.sqlite.org/faq.html#q19) ("SQLite actually waits until the data really is safely stored on the disk surface before the transaction is complete"; update 2024-11-19: "the gist of the answer above remains correct"). Checked 2026-10-13. |
| F3 | With `synchronous=FULL`, SQLite syncs (xSync) so that content is safely written to disk before continuing; FULL is the default with a rollback journal. | established | [SQLite: PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) ("use the xSync method of the VFS to ensure that all content is safely written to the disk surface prior to continuing"; "FULL is the default synchronous mode for a rollback journal"). Checked 2026-10-13. |
| F4 | In WAL mode a commit appends a commit record to the WAL; writers sync the WAL on every commit with `synchronous=FULL` but skip that sync with `NORMAL`. | established | [SQLite: Write-Ahead Logging](https://www.sqlite.org/wal.html) ("A COMMIT occurs when a special record indicating a commit is appended to the WAL"; "Writers sync the WAL on every transaction commit if PRAGMA synchronous is set to FULL but omit this sync if PRAGMA synchronous is set to NORMAL."). Checked 2026-10-13. |
| F5 | WAL with `synchronous=NORMAL` stays consistent (no corruption) but loses durability: a committed transaction might roll back after a power loss or OS crash. An application crash alone does not lose commits in any mode. | established | [SQLite: PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) ("WAL mode is always consistent with synchronous=NORMAL, but WAL mode does lose durability. A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash. Transactions are durable across application crashes regardless of the synchronous setting or journal mode."). Checked 2026-10-13. |
| F6 | `synchronous=OFF` makes commits much faster but the database might become corrupted if the OS crashes or power is lost. | established | [SQLite: PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) ("the database might become corrupted if the operating system crashes or the computer loses power"). Checked 2026-10-13. |
| F7 | Python's `sqlite3` module, by default (legacy transaction control, `isolation_level` not None), implicitly opens a transaction before an INSERT/UPDATE/DELETE/REPLACE when none is open; `isolation_level=None` disables that. `executemany()` uses the same implicit handling. | established | [Python: sqlite3](https://docs.python.org/3/library/sqlite3.html) ("a transaction is implicitly opened before executing sql"; "None to disable opening transactions implicitly"; executemany "Uses the same implicit transaction handling as execute()"). Checked 2026-10-13. Measured: `isolation_level == ''`, `in_transaction` True after the first INSERT (Python 3.12.10). |
| F8 | Measured, default mode (DELETE + FULL), 10,000 inserts: 25,168 ms with a commit per row, 23.6 ms in one transaction (about 1,070×); 2,166 / 240 / 44.8 ms with 10 / 100 / 1,000 rows per commit. | established | Lab and `results.json`; three runs 25.2–26.6 s and 23.6–27.3 ms. |
| F9 | Measured, one commit per row: WAL + FULL 3,389 ms, WAL + NORMAL 249 ms. In one transaction all three modes took 21–24 ms. | established | Lab and `results.json`. |
| F10 | Measured, per-commit cost from a two-point model: 2.51 ms (DELETE + FULL), 0.337 ms (WAL + FULL), 0.0228 ms (WAL + NORMAL); per row about 0.002 ms in every mode. The model was within ±25% for the batch sizes in between in all but one of 27 cells (−40.6%). | simplified | Lab (`fit`, `model_error_pct`); a linear model, not a claim about how SQLite works internally. |
| F11 | Measured, Python default connection: loop + one commit 25.3 ms; commit after every row 23,500 ms; `executemany` + one commit 18.8 ms. | established | Lab (`python_default`). |
| F12 | SQLite supports many simultaneous read transactions but only one write transaction; a connection that tries to write while another is writing fails with `SQLITE_BUSY`. | established | [SQLite: Transaction](https://www.sqlite.org/lang_transaction.html) ("only one simultaneous write transaction"; "the write statement will fail with SQLITE_BUSY"). Checked 2026-10-13. |

## Simplifications register
| # | Simplification | Why it is OK | On-screen caveat |
|---|---|---|---|
| S1 | One machine, one NVMe SSD, Windows. Commit cost depends heavily on drive, cache, file system and OS. | Ratios between batch sizes are the point. | "one laptop · NVMe SSD" |
| S2 | No concurrent readers/writers, no indexes besides the rowid. | Isolates commit cost. | None |
| S3 | `synchronous=OFF` and `EXTRA` are not measured. | OFF is unsafe (F6); EXTRA only adds syncs. | None |
| S4 | The calculator is a two-point linear model (F10). | Error stated next to it. | "estimate, off by up to ~40% between measured points" |
