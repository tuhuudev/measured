# Fact sheet: the N+1 query problem, measured

Every claim in the article maps to these IDs. Levels: established / simplified / contested. Measured rows come from `n1_lab.py` → `results.json` (canonical run 2026-10-12; machine and versions in the JSON).

| ID | Claim | Level | Source |
|---|---|---|---|
| F1 | The "N+1 query" pattern loads a list with one query, then runs one more query per item in the list; it is called the "N+1 Query Problem" or "N+1 Select Problem" and is considered an anti-pattern for client/server databases. | established | [SQLite: Many Small Queries Are Efficient In SQLite](https://www.sqlite.org/np1queryprob.html) ("This is sometimes called the "N+1 Query Problem" or the "N+1 Select Problem" and it is an anti-pattern."). Checked 2026-10-12. |
| F2 | In a client/server database, each SQL statement requires a message round trip from the application to the server and back; hundreds of sequential round trips can be a serious performance drag. | established | [SQLite: np1queryprob](https://www.sqlite.org/np1queryprob.html) ("each SQL statement requires a message round-trip from the application to the database server and back to the application"; "Doing over 200 round-trip messages, sequentially, can be a serious performance drag."). Checked 2026-10-12. |
| F3 | SQLite is not client/server: a query is a function call, not a message round trip, so the N+1 pattern is much less of a problem with SQLite. | established | [SQLite: np1queryprob](https://www.sqlite.org/np1queryprob.html) ("Queries do not involve message round-trips, only a function call."; section title "N+1 Queries Are Not A Problem With SQLite"). Checked 2026-10-12. |
| F4 | Rails example: loading 10 books, then each book's author, executes 1 + 10 = 11 queries; with `includes` the same code executes 2 queries. | established | [Rails Guides: Active Record Query Interface, eager loading](https://guides.rubyonrails.org/active_record_querying.html#eager-loading-associations) ("executes 1 (to find 10 books) + 10 (one per each book to load the author) = 11 queries in total"; "will execute just 2 queries, as opposed to the 11 queries from the original case"). Checked 2026-10-12. |
| F5 | In Rails, `preload` loads each association with one query per association; `eager_load` loads all specified associations with a LEFT OUTER JOIN; `includes` picks between them. | established | [Rails Guides: eager loading](https://guides.rubyonrails.org/active_record_querying.html#eager-loading-associations) ("With preload, Active Record loads each specified association using one query per association."; "With eager_load, Active Record loads all specified associations using a LEFT OUTER JOIN."; "With includes, Active Record tries to load the specified associations using the most performant queries."). Checked 2026-10-12. |
| F6 | In Django, `select_related` creates an SQL join and selects the related object's fields in the same query, but only for single-valued relationships (foreign key, one-to-one); `prefetch_related` does a separate lookup per relationship and joins in Python, retrieving related objects in a single batch, so it is the one for "many" relations such as author → posts. | established | [Django: QuerySet API, select_related / prefetch_related](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#prefetch-related) ("select_related works by creating an SQL join and including the fields of the related object in the SELECT statement."; "select_related is limited to single-valued relationships - foreign key and one-to-one."; "prefetch_related, on the other hand, does a separate lookup for each relationship, and does the 'joining' in Python."; "retrieve, in a single batch, related objects"). Checked 2026-10-12. |
| F7 | Declaring a foreign key does not automatically create an index on the referencing column in PostgreSQL; SQLite does not require one either but says it is almost always beneficial. | established | [PostgreSQL: Constraints, foreign keys](https://www.postgresql.org/docs/current/ddl-constraints.html) ("the declaration of a foreign key constraint does not automatically create an index on the referencing columns"); [SQLite: Foreign key support](https://www.sqlite.org/foreignkeys.html) ("Indices are not required for child key columns but they are almost always beneficial."). Checked 2026-10-12. |
| F8 | SQLite limits the number of `?` parameters in one statement: by default 999 before version 3.32.0 and 32,766 from 3.32.0 on. | established | [SQLite: Limits](https://www.sqlite.org/limits.html) (SQLITE_MAX_VARIABLE_NUMBER "defaults to 999 for SQLite versions prior to 3.32.0 (2020-05-22) or 32766 for SQLite versions after 3.32.0"). Checked 2026-10-12. |
| F9 | Measured, in-process SQLite (no network), loading N authors with 10 posts each: N = 1,000 took 60.4 ms with N+1 (1,001 queries), 14.4 ms with one JOIN, 12.2 ms with two queries (authors, then posts `WHERE author_id IN (…)`). N = 100: 5.81 / 1.27 / 1.10 ms. N = 10: 0.67 / 0.19 / 0.22 ms. | established | Lab `labs/n-plus-one/n1_lab.py`, `results.json` → `in_process`. Checked 2026-10-12. |
| F10 | Measured over TCP on localhost (a small server runs the same SQL; one round trip per query): N = 1,000 took 266 ms with N+1, 29.5 ms with JOIN, 24.5 ms with IN; N = 100: 25.8 / 2.81 / 2.66 ms; N = 10: 2.75 / 0.50 / 0.94 ms. A bare `SELECT 1` round trip took a median 0.114 ms. | established | Lab → `over_tcp`, `tcp_round_trip_ms`. Checked 2026-10-12. |
| F11 | Measured: the same N+1 loop for 100 authors without an index on `posts.author_id` took 602 ms; each per-author query was `SCAN posts` (100,000 rows). With the index it was `SEARCH posts USING INDEX idx_posts_author (author_id=?)` and 5.81 ms. | established | Lab → `no_index_n_plus_one_100`, `index_plan`, `in_process.100`. Checked 2026-10-12. |
| F12 | All three strategies load exactly the same posts (the lab asserts identical post-id sets of N × 10 rows before timing). | established | Lab, `measure()` assertion. Checked 2026-10-12. |
| F13 | Run-to-run variation: comparing three runs on the same machine (two earlier runs and the canonical one), individual medians moved by up to about 40% (mostly sub-millisecond and localhost-TCP figures), while the ordering of the three strategies and the size of the N+1 gap held. | established | Lab runs on 2026-10-12. |

## Model used by the interactive chart
| ID | Formula | Level | Why it is a lower bound |
|---|---|---|---|
| M1 | time ≥ in-process time (F9) + queries × round-trip time | simplified | It ignores sending and decoding the rows. On localhost the measured N+1 cost per extra query was about 0.205 ms ((266 − 60.4) / 1,001), roughly twice the bare round trip (F10), so the model under-estimates. |

## Simplifications register
| # | Simplification | Why it is OK | On-page caveat |
|---|---|---|---|
| S1 | "Over TCP" uses a toy JSON-over-TCP server around SQLite (a thread in the same Python process as the client), not PostgreSQL or MySQL wire protocols. | It isolates the cost the article is about: one network round trip per query. | "a tiny server on localhost, not a real database server" |
| S2 | Localhost is the best case for network latency; real networks add more per round trip. | The model chart lets the reader pick a round-trip time. | Model labelled "lower bound". |
| S3 | Timings include Python's own per-call overhead. | Same for all three strategies; it's part of why N+1 costs more even in-process. | Stated in the data section. |
| S4 | JOIN returns the author's columns repeated on every post row; the IN version returns each author once. The article does not claim one of these two is generally faster. | Measured difference was small and within run-to-run noise at some N. | "Either fixes it" |
