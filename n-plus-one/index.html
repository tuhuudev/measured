The N+1 query problem, measured

Load a list, then run one more query for each item in it. It reads fine in code and works fine on your laptop. Here's what it costs, measured, and why the cost grows with the distance to your database.

Medians of repeated runs. "Over TCP" means a tiny server on the same machine runs the SQL, so every query pays one real network round trip, the shortest one there is.

What N+1 looks like

You show a page of authors with their posts. The natural code is:

authors = db.query("SELECT id, name FROM authors ORDER BY id LIMIT ?", [n])
for author in authors:                       # 1 query above ...
    author.posts = db.query(
        "SELECT id, title FROM posts WHERE author_id = ?", [author.id])   # ... + N queries here

That's one query for the list and one more per item: N+1. It's common enough to have a name, the "N+1 Query Problem", and it's considered an anti-pattern for client/server databases.[1] ORMs make it easy to write without noticing. In the Rails guide's example, loading 10 books and then each book's author runs 1 + 10 = 11 queries.[2]

There are two standard fixes, both returning the same rows:

StrategySQLQueries for N authors
N+1authors, then posts WHERE author_id = ? once per author1 + N
JOINauthors JOIN posts in one statement1
INauthors, then posts WHERE author_id IN (…all the ids…)2

The lab checks that all three load exactly the same posts before timing anything.

Measured: same data, three strategies, two distances

The lab loads the first 1,000 authors and their 10,000 posts. It measures each strategy twice:

  • In-process: Python calls SQLite directly, so there's no network at all.
  • Over TCP on localhost: the SQL goes to a small server on the same machine, so each query is one real round trip.

Over localhost TCP, N+1 was 9 to 11 times slower than either fix. In-process it was still 4 to 5 times slower. Running a statement isn't free even without a network: 1,001 queries in 60.4 ms is about 60 µs each, including Python's own overhead.

Why distance is what matters

With a client/server database such as PostgreSQL or MySQL, every SQL statement is a message to the server and a reply back: one round trip. Hundreds of sequential round trips can be a serious drag.[1] N+1 makes the number of round trips grow with your data. JOIN and IN keep it at one or two.

SQLite is the interesting exception, because it isn't client/server. A query is a function call, not a round trip. SQLite's own docs argue that N+1 is not a problem there.[1] The in-process numbers fit that at small sizes: at 10 authors, N+1 took 0.67 ms. That's slower than a JOIN, but nobody will ever notice. It isn't free, though. At 1,000 authors it still added about 46 ms over the JOIN, with no network involved.

Our localhost server is the best case for a network: same machine, a median 0.114 ms per bare round trip. Most production setups put the database on another machine, so each round trip costs more. Move the slider to see what that does.

Round-trip calculator

Estimate: the in-process time measured above, plus one round trip per query. This is a lower bound for this lab's queries, because it leaves out sending and decoding the rows. Your database's own per-query time can be higher or lower. On localhost, going over TCP added about 0.205 ms per query to the N+1 run, roughly twice the bare round trip. Don't guess your own round-trip time: ping your database host for a first estimate (a real query round trip costs a bit more).

N+1 without an index is far worse

Each of the N extra queries looks up posts by author_id. With an index on that column, SQLite's plan for each one is SEARCHposts USING INDEX idx_posts_author (author_id=?). Without it, every query is SCANposts, a pass over all 100,000 rows. The same N+1 loop for 100 authors went from 5.81 ms to 602 ms, about 100 times slower, with no network involved.

Check that the index actually exists, for example with EXPLAIN on the per-item query. A foreign key alone doesn't guarantee it. In PostgreSQL, declaring a foreign key does not create an index on the referencing column.[3] SQLite doesn't require one either, but its docs say it's almost always beneficial.[4] (Our lab table declares no foreign key at all. The index is what matters for the lookup.)

The fix in your ORM

You rarely write the JOIN or IN by hand. ORMs have a switch for it:

  • Django: for authors → posts (one author, many posts), use prefetch_related. It does a separate lookup per relationship and joins the results in Python, which is the IN strategy. select_related uses an SQL join (the JOIN strategy), but only for single-valued relations: a foreign key or one-to-one, such as going from a post to its author. It can't follow a "many" relation like author → posts.[5]
  • Rails: preload runs one query per association (IN). eager_load uses a LEFT OUTER JOIN (JOIN). includes picks between them.[2] In the guide's books example, includes turns 11 queries into 2.[2]

JOIN or IN? In this lab they were close, and either one removes the N+1. They differ in shape. A JOIN repeats the author's columns on every post row. The IN version sends each author once but needs a second query, and its list of ids can't grow forever: SQLite allows 32,766 ? parameters per statement by default since version 3.32.0, and 999 before that.[6]

How to spot it

  1. Count queries per request, not just time. If the count grows with the number of items on the page, you have N+1.
  2. Test with realistic sizes. At 10 items in-process, N+1 cost 0.67 ms here, invisible on a laptop. At 1,000 items over a network, it's a different story.
  3. Index the column the per-item query filters on, even after you fix the N+1. The fixed queries filter on it too.
  4. Reach for the ORM switch (Django: prefetch_related, or select_related for a foreign key; Rails: includes / preload / eager_load) before writing SQL by hand.

The data

All rows are synthetic. Every timing, plan and count is a real measurement from one run of labs/n-plus-one/n1_lab.py. Raw output: results.json. Machine: AMD laptop, Windows 11, Python 3.12.10, SQLite 3.49.1. Medians of 51 runs, or 21 for N = 1,000, 5 for the no-index loop, and 2,001 for the bare round trip. Run it yourself with python labs/n-plus-one/n1_lab.py (standard library only, about a minute).

Caveats: the "over TCP" server is a toy JSON-over-TCP wrapper around SQLite, running as a thread in the same Python process as the client, not PostgreSQL or MySQL. Every query is still a real TCP round trip. It adds a round trip per query, but not those servers' own protocol and planning costs. Timings include Python's call overhead. Between runs, individual medians moved by up to about 40%, mostly the sub-millisecond and TCP figures. The order of the three strategies and the size of the N+1 gap held.
