Retries, measured: why backoff needs jitter

A server gets busy and starts rejecting requests. Every client retries. Whether everyone gets served in about half a second or keeps getting turned away for seconds depends on one detail: when the retries happen.

The setup

The lab runs a real TCP server in its own process. It handles at most 20 requests at once, 20 ms each. When all 20 slots are taken, it answers "busy" straight away, like an HTTP 503: "unable to handle the request due to a temporary overload".[1]

Then 200 clients each send one request at the same moment. That's a thundering herd, like after a deploy or a cache flush. A client that gets "busy" retries, at most 10 attempts in total, using one of three policies:

# n = 0 after the first failure, 1 after the second, ...
immediate:  wait 0
backoff:    wait min(1000 ms, 10 ms * 2**n)                  # capped exponential backoff
jitter:     wait random(0, min(1000 ms, 10 ms * 2**n))       # "full jitter"

Capped exponential backoff multiplies the wait after each failure, up to a maximum.[2] The jitter version picks a random wait between zero and that same capped value. AWS's article calls this "Full Jitter".[2]

Backoff usually had no failures: in the run shown, at most 5 clients gave up in a trial, and none did in the other two runs. The lab was run three times in full. The run medians for "last client served" ranged 2,379–3,330 ms for backoff and 459–535 ms for jitter. Clients that gave up when retrying immediately ranged 100–120.

Retry immediately: fast, loud, and half or more of the clients fail

The server has 20 slots and each request takes 20 ms. Clients that retry at once burn through all 10 attempts while the slots are still busy. 120 of the 200 clients gave up, and the server took 1,512 requests to serve 80 of them, about 19 requests per success.

Backoff: (almost) everyone gets in, eventually, in waves

Backoff stops the hammering, but every rejected client waits exactly as long as the others. So they come back together, collide again, and 20 get in while the rest are rejected and wait twice as long. You can see the waves below. AWS describes exactly this: "If all the failed calls back off to the same time, they cause contention or overload again when they are retried."[3] The waits double each round until they hit the 1 s cap, so in this run the last clients finished after more than 3 seconds (2.4 s in another).

Jitter: the same backoff, spread out

With jitter, each client picks a random point within its backoff window. Retries spread across the window instead of landing together, so free slots get used as they open up. Every client got in, and the last one finished at 459 ms. The request count was only a bit lower than plain backoff (901 vs 1,063). In this setup, the big win is time: across the three lab runs, the last client was served about 4 to 7 times sooner (7 times in the run shown).

Try it: the same model, simulated

This simulation uses the same server model, the same three policies and the same backoff numbers. You can change the number of clients and the network round trip. It's a simulation, not a measurement. It has no scheduling noise, so waves without jitter stay perfectly lined up, which is a bit worse than the lab, where noise broke some of them.

Server: 20 slots, 20 ms per request, "busy" at once when full. Clients: all start at 0, at most 10 attempts, backoff 10 ms doubling to a 1 s cap. With jitter, the outcome depends on the seed. Across 30 seeds at 200 clients and the default round trip, the simulated jitter run sent a median 971 requests, and its last client finished at a median 451 ms (range 378–964 ms). That's close to the lab's 901 requests and 459 ms. Because nothing in the simulation adds noise, plain backoff keeps its waves perfectly aligned, and its last wave runs out of attempts. Immediate retries also fail more often here than in the lab, because the lab's Python clients are slower between attempts.

What to do in your code

  1. Back off and add jitter. Google's SRE book is blunt: "Always use randomized exponential backoff when scheduling retries."[4] AWS's simulation found that backoff without jitter "helps a small amount, but doesn't solve the problem".[2]
  2. Cap the attempts. "Limit retries per request."[4] A cap only bounds the damage. Without a wait between attempts, the cap just decides how fast clients give up, as the immediate-retry row shows.
  3. Consider a retry budget for the whole process, such as at most 60 retries per minute, failing the request instead of retrying once it's spent.[4] Not measured here.
  4. Listen to the server. A 503 may come with a Retry-After header telling you when to come back.[1]
  5. Only retry what's safe to repeat. HTTP says a client SHOULD NOT automatically retry a non-idempotent request (a POST that creates an order, say) unless it knows repeating it is safe, or can tell the first one was never applied.[5]

The data

Every number in the table and the timelines is a real measurement from labs/retries/retry_lab.py. Raw output: results.json, and the two other full runs in runs/. Machine: AMD laptop, Windows 11, Python 3.12.10. Each policy ran 7 trials, and the table shows the medians. Seeds fix the random draws, not the timing, so re-runs vary (the ranges above). Run it yourself with python labs/retries/retry_lab.py (standard library only).

Caveats and one correction made while building the lab:

  • Windows timer. By default, Windows rounds asyncio.sleep up to its timer tick of about 15.6 ms. A 20 ms sleep measured about 32.6 ms, which would have distorted every wait. The lab asks for a 1 ms timer (timeBeginPeriod(1)), after which a 20 ms sleep measured about 20.6 ms.
  • Clients share one event loop. All 200 clients run in one Python process, which sends in small batches a few milliseconds apart. That timing noise affects every policy. It bunches jittered retries a little, but it also breaks up some of backoff's waves: the noise-free simulation is harsher on backoff than the lab. Its net effect on the gap isn't measured here. It's also why the timelines use 50 ms buckets.
  • Toy server. It rejects instantly when full. Real servers may queue, slow down or time out instead. There's a single burst of clients and no new traffic. Other jitter variants (AWS's article also tests "equal" and "decorrelated" jitter), retry budgets and Retry-After are not measured.
