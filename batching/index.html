Batching writes, measured: one transaction vs one per row

Inserting a row is cheap. Committing is not. The same 10,000 rows took 25 seconds or 24 milliseconds, depending only on how many commits they were split into.

Medians of 3 trials, each into a fresh database file. In three full runs of the lab: 25.2–26.6 s and 23.6–27.3 ms. A different drive or OS will give other numbers; the ratio, about 1,000×, is the point.

Unlike the other articles here, this one touches the disk on purpose, because that's where the cost is. SQLite's FAQ puts it plainly: it can do far more inserts per second than transactions, and "by default, each INSERT statement is its own transaction".[1] Below: how the time depends on rows per commit, what WAL mode and synchronous=NORMAL change (and what they give up), and a Python detail that decides which case you're in.

Why a commit is expensive

When a transaction commits, SQLite by default waits until the data is safely on the disk before it reports success, so a power cut or an OS crash can't lose it.[1] With synchronous=FULL, the default with a rollback journal, it asks the OS to sync the content to the disk before continuing.[2] That wait is paid per commit, not per row. Wrap many inserts in one BEGIN … COMMIT and the commit cost is shared among all of them.[1]

Measured: rows per commit

The lab inserts 10,000 rows of about 110 bytes into a new database file, with a COMMIT after every 1, 10, 100, 1,000 or all 10,000 rows, in SQLite's default mode (rollback journal, synchronous=FULL):

Ten rows per commit is already ten times faster than one, and a hundred is a hundred times faster. After that the gains flatten out: once commits are rare, what's left is the work of the inserts themselves. A simple model fits that shape: total ≈ commits × 2.51 ms + rows × 0.0021 ms. On this SSD, one commit cost about as much as 1,200 inserts.

WAL and synchronous=NORMAL

SQLite has a second journal mode, write-ahead logging (WAL). A commit there appends a commit record to the WAL file. With synchronous=FULL the WAL is still synced on every commit. With synchronous=NORMAL that sync is skipped.[3]

WAL with FULL made per-row commits about 7 times faster on this machine, and WAL with NORMAL about 100 times faster. But read what NORMAL gives up. WAL with synchronous=NORMAL never corrupts the database, but "a transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash".[2] That's fine for a cache or analytics events. It's not fine for an order you've already confirmed to a customer. (An application crash alone doesn't lose commits in any mode.[2]) And synchronous=OFF, which the lab didn't measure, can corrupt the database on an OS crash or power loss.[2]

Look at the last column, though. In one transaction, all three modes took 21–24 ms. Batching made the mode choice almost irrelevant for this workload, without trading away any durability.

The Python detail that decides which case you're in

Python's sqlite3 module, by default, opens a transaction for you before an INSERT, UPDATE, DELETE or REPLACE, and keeps it open until you call commit().[4] The lab confirmed it: with a default connection, in_transaction was already True after the first insert. So with the defaults, the commit pattern is whatever your commit() calls say:

Default connection, SQLite defaults, 10,000 rowsMedian
 
db = sqlite3.connect('app.db')        # implicit transactions (the default)
for row in rows:
    db.execute('INSERT INTO events (ts, payload) VALUES (?, ?)', row)
db.commit()                           # one commit: fast

db = sqlite3.connect('app.db', isolation_level=None)   # autocommit
for row in rows:
    db.execute('INSERT ...', row)     # every statement commits: slow

The slow case shows up in real code as a commit() inside the loop, often hidden in a helper like save(item) that commits "to be safe", or as a connection in autocommit mode (isolation_level=None, which disables the implicit transactions[4]). executemany() uses the same implicit transaction[4], and with one commit it was the fastest variant here.

Estimate your own batch

Batch calculator

Estimate: commits × per-commit cost + rows × per-row cost, using the costs measured above for each mode. The model comes from the 1-row and 10,000-row measurements. For the batch sizes in between it was within ±25% of the measured value in 26 of 27 cases, and off by 41% in one. The lab only inserted 10,000 rows, so larger row counts are an extrapolation. Per-commit costs depend heavily on your drive and OS: the shape will carry over, the absolute numbers won't.

Rules of thumb

  1. Commit per unit of work, not per row. Importing a file, processing a queue batch, seeding a database: one transaction, or batches of a few hundred to a few thousand rows.
  2. Find the hidden commits. A commit() inside a loop or inside a per-item helper, or a driver in autocommit mode, gives you the slow column.
  3. Batching beats tuning. Batched, all three modes were within a few milliseconds of each other. Change synchronous only if you've decided which commits you can afford to lose.
  4. Batches have a ceiling too. SQLite allows only one write transaction at a time, so while a long one is open, other connections that try to write get SQLITE_BUSY.[5] And if a batch fails, all of it rolls back. Past about 1,000 rows per commit, the gain here was under 2×.

The data

All rows are synthetic. Every timing is a real measurement from one run of labs/batching/batching_lab.py. Raw output: results.json, and two more full runs in runs/. Machine: AMD laptop, Windows 11, Python 3.12.10, SQLite 3.49.1, database files on an NVMe SSD. Medians of 3 trials, each into a new file. Timings include Python's call overhead. Run it yourself with python labs/batching/batching_lab.py (standard library only, about 3 minutes).

Caveats: one machine and one drive. Commit cost depends on the drive, its write cache, the file system and the OS, so expect other absolute numbers. Single writer, no concurrent readers, no secondary indexes. Individual trials varied more than the medians: in one run, a single default-mode trial at 100 rows per commit took 1,120 ms against a median of 314 ms. Client/server databases add a network round trip per statement on top, which this lab doesn't measure.
