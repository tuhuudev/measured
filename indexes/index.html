Database indexes, measured

Which queries an index actually speeds up, which ones it silently can't, and what every extra index costs you. Every number here comes from one script you can run yourself.

Published 2026-10-12 · SQLite 3.49.1 · 1,000,000 rows · one laptop · lab code

Find one email, no index
64.2 ms
SCANusers
Same query, index on email
0.0031 ms
SEARCHidx_email (email=?)

Medians of repeated runs on an in-memory database, so no disk and no network are involved. Your machine will give other numbers; the gap between them is the point.

That is about 20,000 times faster for adding one line of SQL. It's also why "just add an index" is the usual advice, and why it's incomplete. The same index did nothing for three other queries on the same column. It made the database 53% bigger, and it made every insert slower. Below, each of those claims is measured, and you can run the queries yourself in the playground.

Without an index, the database reads every row

Ask for WHERE email = 'user777777@example.com' on a table with no index, and the database has no idea where that row lives. It has to scan the entire table, row by row, and check each one.[1] SQLite's plan says exactly that: SCANusers. On one million rows that took a median 64.2 ms.

A scan costs time proportional to the number of rows, N. Double the table and you double the wait.[2]

What an index is

An index is a separate structure that keeps one column's values in sorted order, each with a pointer back to its row. Because it's sorted, a lookup costs about log N steps instead of N.[2]

The usual shape is a B-tree, a tree of fixed-size pages. Upper pages point to the next level down, and leaf pages hold entries that point to table rows.[3] A lookup walks a few levels down that tree instead of scanning.[1] B-tree is the default: CREATE INDEX in PostgreSQL creates one unless you ask for something else.[4]

Three levels for a million entries is why the lookup is so fast. The database reads one page per level, then follows the pointer. With the index in place, the plan becomes SEARCHusers USING COVERING INDEX idx_email (email=?), and the median time drops to 0.0031 ms. COVERING means the index alone holds every column the query asked for, so the table itself isn't read at all.[6] Our query only selected id, which SQLite keeps inside each index entry. A SELECT * would add one hop from the index to the row.

Queries an index helps

A B-tree index serves conditions on data that can be sorted: =, <, <=, >, >=, BETWEEN and IN.[4] For a range, it searches once for the first matching entry and then reads the following entries in order.[2] Our email BETWEEN 'user5' AND 'user6' was a SEARCH(email>? AND email<?).

It also helps with sorting. An index already holds rows in order, so ORDER BY email needs no separate sort. With LIMIT 10, the first ten rows come straight off the index without the rest being read.[7] Without the index, SQLite scanned everything and built a temporary B-tree to sort it (USE TEMP B-TREE FOR ORDER BY), which took 93.7 ms. With the index it took 0.0052 ms.

Queries the same index can't help

An index only helps when the query can follow its sorted order. With idx_email in place, all three of these were still scans:

  • A different column. WHERE name = ? took 69.3 ms with SCANusers. The email index knows nothing about names.
  • A pattern that doesn't start at the beginning. In WHERE email LIKE '%777@example.com' the start of the string is unknown, so there is no place in the sorted order to jump to.[4] SQLite read the whole index instead (SCAN users USING COVERING INDEX idx_email). That's still a scan.[6]
  • A function wrapped around the column. WHERE lower(email) = ? took 196.9 ms. The index stores email, not lower(email). SQLite's docs put it bluntly: the planner "does not do algebra".[8]

The fix for the last one is an index on the expression itself, CREATE INDEX idx_lower_email ON users(lower(email)). With it the plan became SEARCHidx_lower_email (<expr>=?) at 0.0031 ms. The query has to write the expression exactly as the index does.[8] And an expression index is extra work on every insert and update, because the expression is computed for each row.[9] Often the cheaper fix is to store emails lowercased in the first place and compare the column directly.

Multi-column indexes: the leftmost column decides

An index on (last_name, first_name) is sorted by last_name first. first_name only breaks ties within the same last name, like a phone book.[2] It's most efficient when the query constrains the leading column. Conditions on later columns alone don't necessarily narrow what has to be read.[10]

Query, with index on (last_name, first_name)PlanMedian
last_name = ? AND first_name = ?SEARCH0.0038 ms
last_name = ? (1,000 matching rows)SEARCH0.366 ms
first_name = ?SCAN whole index63.9 ms
first_name = ? after ANALYZESEARCH ANY(last_name)2.55 ms

The last row is a skip scan. When the first column has few distinct values, the database can do one search per distinct last name. SQLite only considers this after ANALYZE has measured how many duplicates there are.[11] PostgreSQL 18's B-tree can skip scan too, under similar conditions.[10] It beat the full scan, but it was still about 670 times slower than the query that named both columns. Put the column you always filter on first.

What every index costs

An index is a second copy of your data that the database has to keep in sync with the table. That adds overhead to every insert, update and delete.[1] When a leaf page fills up, it splits: some of its entries move to a new page and the parent gets a new pointer. Splits can cascade up, and a root split adds a level.[3]

One index made the insert batch 47% slower. Three made it 2.7 times slower. Space costs too: adding the email index grew the database from 59.1 MB to 90.2 MB, which is 53% bigger for one index on one column.

Read the plan before you add an index

Every database will tell you what it plans to do, and you don't have to guess.[12]

-- SQLite
EXPLAIN QUERY PLAN SELECT id FROM users WHERE email = ?;
--> SEARCH users USING COVERING INDEX idx_email (email=?)

-- PostgreSQL
EXPLAIN SELECT id FROM users WHERE email = $1;
--> Index Scan using idx_email on users ...

In SQLite, SCAN means every row, or every index entry, is visited. SEARCH means only a subset is.[6] In PostgreSQL, a full scan shows as Seq Scan and index access as Index Scan, Index Only Scan or Bitmap Index Scan + Bitmap Heap Scan.[12]

Rules of thumb

  1. Read the plan first. If it already says SEARCH or Index Scan, a new index won't help.
  2. Index the columns you filter, join or sort on, and write the condition on the bare column: email = ?, not lower(email) = ?.
  3. In a multi-column index, put the column you always filter on first.
  4. A leading wildcard (LIKE '%x') can't use a B-tree index to narrow the search.
  5. Every index slows every write and takes disk space. Drop the ones no query uses.
